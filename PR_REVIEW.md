# PR #412 review — Track: load transactions from the new API

Review of `review/TrackScreen.tsx` and `review/useTransactions.ts` from the supplied mock repo. Highest impact first.

1. **Block — the fixture is not one transaction schema.** `Txn` requires `occurred_at`, `direction`, `amount_minor`, and `merchant`, but 2,281 records use `txn_time`, `type`, decimal-string `amount`, and `merchant_name`. They render with missing dates/merchants and invalid month groups, and their money is silently lost. Normalize both shapes at the API boundary; preserve optional metadata.
2. **Block — the page cursor repeats a boundary row.** The API's full-list pagination starts the next page at the previous page's last index. `setTransactions([...transactions, ...body.items])` therefore duplicates that transaction. Upsert by stable transaction ID, using `updated_at` to resolve versions.
3. **Block — the hook never consumes the changes feed.** It ignores `sync_token` and `/transactions/changes`, so it cannot apply new rows, corrections, or tombstones. The fixture starts with 25 pending rows; the delta settles 18 and removes 7. A full snapshot must be followed by the delta, with the final token committed with that state.
4. **Block — failed sync destroys visible history.** The catch handler sets transactions to `[]`, then the screen replaces the whole view with an error. Keep the last committed snapshot visible and surface a retry state; only replace it after a complete successful sync.
5. **Block — no HTTP status handling or transient retry.** `fetch` does not reject for HTTP 429/500/503, so `res.json()` can return `{error: ...}` and the hook treats it as a page. This server deliberately returns 500 and 429 during a full pull and 503 on the first delta request. Check `res.ok`, honor `Retry-After`, and retry transient errors without committing a new cursor.
6. **Block — monthly totals do not match the meaning of money here.** The PR sums every debit, omits income, treats internal account/card payments as spending, and formats USD minor units as rupees. The fixture has 50 own-account transfers and 15 USD rows with `fx.inr_minor`. Exclude only own transfers, use integer paise, use the supplied INR equivalent for INR month totals, and leave real `TRANSFERS_OUT` spending in the totals.
7. **Block — month keys use UTC string slices.** `occurred_at.slice(0, 7)` buckets by UTC, which misplaces transactions around India midnight/month boundaries. Convert timestamps into Asia/Kolkata before grouping and labelling; use the same rule for the checkpoint.
8. **Block — required user flows are absent.** There is no merchant search or transaction detail view, and the row schema does not retain extra transaction fields. Add local search and a detail sheet that renders the fields actually returned.
9. **Allow with a follow-up — index keys and overlapping loads.** `keyExtractor` uses array position, and `onEndReached` can trigger multiple requests against the same cursor before state updates. Use transaction IDs for row keys and serialize or guard in-flight pagination. This is less severe than data loss/corruption, but can produce row reuse and duplicate appends under fast scrolling.

## Corrections made in this implementation

The app normalizes both record shapes, deduplicates page boundaries, applies changes and deletions using update timestamps, retries 429/5xx responses, retains a committed offline snapshot, calculates India-local totals in paise with FX conversion, and includes merchant search and transaction detail. Fixture tests reconcile the final 4,686 IDs and every supplied month total.
